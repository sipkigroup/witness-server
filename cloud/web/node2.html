Deus Witness™

Node 2: independent co-signer

Test stage. The only real attestation report so far (22 October 2026) was taken with an allow-all container policy, used for a probe. With such a policy the operator (we) can run commands inside the container next to the key, so node 2 is not independent of us yet, and the checker says NOT COVERED. This page shows what node 2 publishes; the verdict is yours to compute.

What node 2 does

Every anchor batch of the witness (node 1) holds a signed checkpoint of each journal that changed. Node 2 receives each batch with, per journal, a proof that the new journal tree extends the last one node 2 co-signed (an RFC 9162 consistency proof). If all of it holds, node 2 co-signs the batch with its key K2. If node 1 shows another tree of the same size, a smaller tree, or cannot prove the extension, node 2 signs an alarm that carries both checkpoints: anyone can check it offline.

Node 2 never sees journal entries, only the hashes of the checkpoints. Its key is created in the memory of an AMD SEV-SNP confidential container (Azure Container Instances) and is bound to an AMD-signed attestation report. A restart creates a new key; the list below shows every key with its report.

FORK (same size, other tree) and ROLLBACK (a smaller tree signed later) are definitive. NOT_PROVEN_APPEND_ONLY means node 1 could not prove that a journal only grew; it is not by itself proof of a rewrite. Every co-signature counts the alarms raised before it, so an alarm that disappears from this list is visible in the next co-signature.

Check it yourself

  1. Download your evidence pack (Dashboard, Export) and unzip it.
  2. Run the checker from a source you trust, not from the pack: 
    python -I pack/verify/verify_pack.py pack --offline
    The line node2: says COVERED, NOT COVERED (with the reason) or ALARM.
  3. Keep the file node2-pin.json that the checker writes next to the pack folder. On the next check it detects a node 2 restarted from an old state (the chain it is shown differs from the one you saw).
  4. Pin the expected build: --node2-expect=expect.json with {"policy_sha256": ..., "measurement": ...} recomputed from the open node 2 image, and --node2-genesis=<hex> once the genesis is published.
  5. The raw data: GET /v1/node2/keys, /v1/node2/latest, /v1/node2/chain?from=1, /v1/node2/alarms. All of it is signed by K2 or AMD; node 1 only relays it.

What this does not prove

  • Anything before node 2 first saw your journal: the first checkpoint it sees is taken on trust.
  • That Microsoft and AMD are honest: they sign the platform and the utility VM. One cloud and one chip maker are a single trust boundary.
  • That the container runs the published node 2 code, until the policy is not allow-all and you compared its hash with your own build.
  • That node 1 shows node 2 your journal at all: if it does not, your checkpoints stay without a co-signature, and the checker says NOT COVERED. The absence is the signal, so a checker that you run is needed.
  • Freshness: the time inside a co-signature is node 1's batch time; node 2 has no clock of its own yet.
  • Revocation of AMD certificates and a minimum firmware level are not checked offline.
