What the witness sees - and what it does not

Deus Witness judges the tool calls that are sent to it: through the MCP proxy, the Claude Code hook, or the SDK. Each judged call gets a verdict (allow, deny, hold for your approval) and a signed receipt. It is a checkpoint, not a monitor.

What Witness protects

  • Deletion - deleting or overwriting data is judged against what your mandate allows; irreversible deletes are held for you.
  • Sending data out - messages, uploads and publishing go only to recipients and channels you listed.
  • Secrets - API keys, credentials and data you marked as closed are not allowed to leave in the text of a call.
  • Money - purchases are checked against the budget and per-purchase limit you signed.
  • Commands outside what you allowed - shell commands that your mandate does not cover are held for your approval, and clearly dangerous ones are always asked about.
  • The default shell list (server 0.2.55) - the default mandate (the one you sign on the Mandate page) runs 67 commands without a question: 52 that only read and print (ls, cat, grep, find, sed, awk, jq, sort, diff, git status, git log and so on) and 15 local writes (mkdir, touch, cp, mv, ln, chmod, rm, rmdir, git add, git commit, git checkout, git switch, git restore, git mv, git rm). A trial account made with deus-witness try gets this same default list (67 commands: 52 reads and 15 local writes) in its drafted mandate.

- find, sed, awk and jq run unasked only in the form that reads and prints. Running another program (find -exec, sed with e, awk with system() or a pipe), writing (find -delete, sed -i, awk with >) or reading a file outside the project is asked.

- A write command is covered only when every path it touches is inside the project or a temp directory and none is protected (agent configuration, .git, credential files, Witness keys). Anything else is asked: paths outside, unclear options or wildcards, recursive or forced forms (rm -r, git add -f), protected paths.

- Searching or listing a whole tree outside the project is asked: grep -r, rg, grep -d recurse, git grep, ls -R, du -a, tree. One level is not (ls ~, du -sh ~).

- Interpreters, package managers and anything that sends data are asked. The first button on the approval page is "Allow for 24 h in this project", then "Approve once" and "Refuse". A dangerous command (rm -rf, git push --force, curl ... | sh and the like) is never offered "Allow for 24 h": the page has only "Approve once" and "Refuse", and it asks again every time.

  • Test runners in Claude Code's strict sandbox (server 0.2.57, client 0.2.39) - a test runner (pytest, python -m pytest, python -m mypy, ruff, npm test, npm run, npx jest, npx tsc, cargo test, go test, make and similar) runs code the agent may have written, so by default it needs your approval. If your mandate says "Test runners in Claude Code's strict sandbox: run without asking" (the default of a new mandate) and the hook reports that this very call runs inside a strict Claude Code sandbox, the runner runs unasked and the receipt says sandboxed. Without that sandbox, or with a mandate signed before this option, runners are asked as before. Strict means (server 0.2.57): macOS, and three places set as follows.

1. Your user settings ~/.claude/settings.json (or managed settings) lock the network. Claude Code ignores this key in a project's settings, and the hook cannot see --settings:

```json

{ "sandbox": { "network": { "strictAllowlist": true } } }

```

2. The project's .claude/settings.json:

```json

{

"sandbox": {

"enabled": true,

"failIfUnavailable": true,

"allowUnsandboxedCommands": false,

"filesystem": { "denyRead": ["~/", "./.env"], "allowRead": ["."] }

}

}

```

3. The environment Claude Code is started from: export CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1. A settings env block does not turn the scrub on.

These are Claude Code's own keys (code.claude.com/docs/en/sandboxing). failIfUnavailable stops Claude Code from falling back to running commands unsandboxed, and "with the retry disabled, Claude Code ignores the dangerouslyDisableSandbox parameter". Without strictAllowlist, bypassPermissions mode lets a sandboxed command reach any host; with it, "the built-in sandbox proxy refuses the connection in every permission mode". The permission mode has to be default, acceptEdits or bypassPermissions (that includes --dangerously-skip-permissions). In auto, plan and dontAsk the runner is asked until those modes have been checked. sandbox.excludedCommands and sandbox.network.allowedDomains must stay empty. There must be no Unix sockets and no weakening keys, and every .env file of the project must be unreadable. If any of these is missing, a settings file cannot be read, or you are on Linux or Windows, the sandbox counts as "not strict" and the runner is asked. Installers (npm install, pip install) and interpreters (python3 script.py) are always asked. Known limits: the hook cannot see settings passed with --settings or server-managed settings, so a lock set there counts as missing. The scrub also removes DEUS_WITNESS_KEY from the hook's environment, so give the hook its key with the key file that deus-witness try saves, not an environment variable.

  • Switching branches - git checkout <branch> and git switch <branch> can rewrite tracked files, including agent configuration. With a current hook, the switch runs unasked only if it changes ordinary files; if it touches protected files, .gitattributes, .gitmodules, a submodule or a post-checkout hook, you are asked. With an older client (0.2.36) you are asked on every switch. Such a question cannot be turned into a standing project permission. Known limits: the check is made when the call is judged, not when it runs, and a repository with a post-checkout hook (for example husky) is asked on every switch.
  • Changes to the project's own executable files - a command that runs files the agent has just changed is held for your approval.
  • Unknown programs after a risky write - once a call has written a file in a risky way, any program the witness does not know as read-only or as a local write is asked, not only known interpreters. Allowing a wrapper (xcrun, uv run, tmux, fd -x, git bisect run and similar) does not cover the program it starts: that program is judged on its own. Options that make a reader run code (tar --to-command, man -P, less +!cmd, rsync -e, find -exec, also in shortened long forms) are asked.
  • Configuration files that are code - a linter or test configuration, and git hooks (.git/hooks, core.hooksPath inside the project), count as code the agent can change; running the tool after such a change is asked.
  • The agent's own settings, git hooks and git configuration (server 0.2.77, client 0.2.51) - a write into .claude/ (settings, hooks), .claude.json, .mcp.json, or into another agent's or editor's configuration from this list (.cursor/hooks.json, .gemini/settings.json, .vscode/tasks.json, .windsurf/*.json, Windsurf's mcp_config.json, .roo/mcp.json, .kiro/settings and .kiro/hooks, .amazonq/mcp.json and its agents, opencode.json), into .git/config, or into a git hook is always asked. A git hook is a file in .git/hooks, or a file with a git hook's name (pre-commit, ...) or under a hooks folder (.husky, .githooks, githooks, .git-hooks, git-hooks; husky 9's .husky/_) in any core.hooksPath that git reads from files: the repository's own, your ~/.gitconfig, $XDG_CONFIG_HOME/git/config or ~/.config/git/config, the system files (/etc/gitconfig and Homebrew's), and every file they include (include.path, includeIf.*.path; the includeIf condition is not evaluated, the path is always followed). The approval page names the real file, not the name the agent used: "Your agent wants to change its own settings, the file:" / "...a git hook, the file:" / "...git's configuration, the file:", and "(it writes through notes.md, a link to this file)" when the agent wrote through a link. A hard link to such a file is judged as that file; this needs client 0.2.51 (the hook tells the witness which protected file a name with several links is); with an older hook, nothing changes for hard links, and a global core.hooksPath is not read.
  • An approval given after the agent stopped waiting (server 0.2.77) - if you approve a command after the hook stopped waiting, the same command repeated within the 15 minutes the request stays open still runs. If, after the question, the witness let through a write by the same agent (anywhere), or by another agent of your account into the command's project, the repeat does not get that approval: the old request ends as "a file changed" and you are asked again, with the text "You approved this command before. After your approval the agent wrote a file (...) before it repeated this command, so your approval was not used and nothing ran on it." A document (.md, .markdown, .rst, .adoc, .log) that the command does not name and that nothing in the command executes does not end the approval. A repeat with nothing written in between keeps it.
  • Freeze after a refusal (server 0.2.77) - after you refuse a call, the result screen has "Freeze this agent". If the same agent's next call is opened in the same browser tab within 10 minutes, the button is also on the first screen of the new question; on another device it is under Details.

Every decision is written to a signed, append-only ledger that you or an outsider can re-check offline.

What Witness does NOT do

  • It is not a sandbox. It does not stop a process; it decides on calls that are shown to it.
  • It sees only what goes through the hook, the MCP proxy or the SDK. Another tool server, a built-in tool you did not route, a direct network call or code the agent runs on its own leaves no receipt.
  • It does not read intent. Content checks are deterministic and can be evaded by rewording; the recipient list is the stronger barrier.
  • Code the agent runs is read, not executed. For interpreter code in a command line (python -c, node -e, perl -e, awk, pipes into an interpreter) and for files the agent wrote and then runs, the witness looks for network calls, literal hosts, /dev/tcp and code that builds what it runs (exec, eval, decoders, names glued from pieces); such code is asked as dangerous and shown to you. Known limits: a host assembled at run time without any of those primitives and passed to a library the scanner does not know is not seen; a file the agent changes after you approved its preview, or beyond the first 4 KB, is not shown; a file written in one call and run in a later call is asked once when the write was unseen or risky (ESCALATE_WRITTEN_RUN; the page shows the file and how it was written), but the link between the two calls is followed for copies, redirections, renames and cd, not for every shell trick. The mandate's recipient list and a sandbox stay the stronger barriers.
  • Limits of the code scan. A URL built at run time without any of the primitives above and passed to a function that is not on the scanner's list is not seen. Linter and type-checker plugins are not seen when the configuration file is unchanged: the server gets the hash of the configuration, not its text.
  • Code from a remote branch. The text that git pull or merge brings is not shown on approval pages. Pull itself is asked unless the mandate allows it, and running code after a pull or merge that followed a secret is asked again.
  • Links to credential files (server 0.2.73, client 0.2.49). A hard or symbolic link to a credential file is judged as that file: reading it is asked, and after you approve it the "secret read" state applies. ln and unpacking a tar or zip that creates such a link are asked with the reason named (the client reads only the archive headers and unpacks nothing). Known limits: with the witness reachable, Grep over a directory can still print an existing hard link to a secret that has a plain name; a compressed archive over 16 MB is not read and stays an ordinary question.
  • A coverage level is the operator's own statement, not something Witness verifies.
  • It cannot make an approval screen honest by itself: you trust the page you sign on; its script hashes are published on the home page.
  • It is as independent as its operator. At this stage the operator is the author of the project.
  • If the witness cannot be reached, calls are blocked (fail-closed), with one exception: from client 0.2.48 a call that only reads a non-secret file inside the project is not blocked by the hook (Claude Code's own permission rules decide), one line goes to the local offline.log and the user gets one message. Everything else (writes, running code, network, MCP, git, secret paths, anything outside the project) is still denied. This applies only to network errors, 5xx and timeouts: a 401, 429, other 4xx or a damaged reply is a denial. DEUS_WITNESS_HOOK_OFFLINE=strict restores denial of everything. From client 0.2.49 a read of a file that has more than one name (a hard link) is also denied while the witness is down, and so is Grep while a credential file of the project has more than one name. Caveat: if you made a read an approval question, it passes without the question while the witness is down; use strict for that. The MCP proxy still denies everything when the witness is unreachable.

Known limitations

Witness sees only the calls your agent makes. A file changed by something you already let run (a build, a watch process, a git hook, your editor) or by you is invisible to it, so approving "run this script" after such a change may run the new text. Instruction files (CLAUDE.md, AGENTS.md, rules folders) are not guarded: an agent can leave notes for its next session there; every risky call that follows still goes through Witness. Other tools' configuration in the project is guarded only for the files we list (Claude Code, MCP configs, Cursor hooks, Gemini CLI, VS Code tasks, Windsurf, Roo, Kiro, Amazon Q, opencode). Git hooks are guarded in .git/hooks and in every core.hooksPath git reads from files (the repository's, husky, your ~/.gitconfig and the files it includes); a hooks path set only in your shell's environment (GIT_CONFIG_GLOBAL, -c) is not seen. Case-folded .GIT and hard links are partly checked by the client: update to 0.2.51+. The hard-link search walks at most 20,000 project entries; beyond that, a write to a file with several names is asked.

More, from the 0.2.77 / 0.2.51 review:

  • Hard links: links to hooks of nested repositories or submodules (sub/.git/hooks) and to files under ~/.claude/ other than the settings files are not searched. In a very large project (pnpm keeps hard links in node_modules) the cut walk can make a write to any file with several names a question.
  • Git hooks: a file in a hooks folder that does not have a hook's name (a scripts/git/helper.sh that a hook calls) is an ordinary write. At most 16 hooks-path values and 32 config files are read; more are dropped without a question. A system git built with another prefix (for example Xcode's share/git-core/gitconfig) is not read. The key core.pager, an alias starting with ! or git's file-system-monitor program key in a file that the global config includes is not judged; only the repository's config is.
  • Approval after the agent stopped waiting: a write the witness does not see (a program you let run, you by hand, someone else's git checkout), and a write by another agent of your account outside the project, do not end the approval. A script that itself reads a .md, .rst or .log the command does not name is not covered by the document rule. If the agent rewrote a file and repeated the call before you approved, the page shows you the command, not the new text of the file.
  • Client and server versions: with a hook older than 0.2.51 the hard-link and global core.hooksPath checks do not work (the server-side checks still do). With 0.2.50 or older, a hard link to .claude/settings.json is written without a question; creating the link (ln, cp -l) is asked.
  • Not tested on a real iPhone. The list of other agents' configuration files comes from their documentation; whether those programs run them was not checked.

To close the gaps, route every tool through Witness, deny other executing tools in the client, and run the agent in a sandbox. See also the Concepts page for what is proven and what is not.
